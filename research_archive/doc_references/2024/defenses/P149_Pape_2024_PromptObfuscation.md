### Abstract original
> "System prompts that include detailed instructions to describe the task performed by the underlying LLM can easily transform foundation models into tools and services with minimal overhead. They are often considered intellectual property, similar to the code of a software product, because of their crucial impact on the utility. However, extracting system prompts is easily possible. As of today, there is no effective countermeasure to prevent the stealing of system prompts, and all safeguarding efforts could be evaded. In this work, we propose an alternative to conventional system prompts. We introduce prompt obfuscation to prevent the extraction of the system prompt with little overhead. The core idea is to find a representation of the original system prompt that leads to the same functionality, while the obfuscated system prompt does not contain any information that allows conclusions to be drawn about the original system prompt. We evaluate our approach by comparing our obfuscated prompt output with the output of the original prompt, using eight distinct metrics to measure the lexical, character-level, and semantic similarity. We show that the obfuscated version is constantly on par with the original one. We further perform three different deobfuscation attacks with varying attacker knowledge—covering both black-box and white-box conditions—and show that in realistic attack scenarios an attacker is unable to extract meaningful information. Overall, we demonstrate that prompt obfuscation is an effective mechanism to safeguard the intellectual property of a system prompt while maintaining the same utility as the original prompt."
> — Source : PDF page 1

### Resume (5 lignes)
- **Probleme :** Le system prompt d'un LLM (souvent considéré comme propriété intellectuelle, "considered intellectual property, similar to the code of a software product", Abstract, p.1) est trivialement extractible par prompt injection / prompt-stealing — les auteurs rappellent que des milliers d'outils commerciaux (Microsoft Bing, Copilot, Notion AI, plusieurs modèles OpenAI) ont vu leur system prompt fuité "even word for word" (Section 1, p.1-2). Constat de départ : "currently, there are no successful strategies to prevent the stealing of system prompts, and all safeguarding efforts could be evaded" (Section 1, p.2). Le problème n'est donc PAS d'empêcher la fuite mais de la rendre inutile.
- **Methode :** Plutôt que de bloquer la fuite, les auteurs proposent l'**obfuscation du system prompt** : trouver une représentation `s_obf` qui (1) préserve la fonctionnalité de `s` et (2) reste inintelligible pour un adversaire même si elle est exfiltrée (Section 3.2, p.4). Deux variantes : **hard prompt obfuscation** (espace des tokens, optimisé par GCG — Greedy Coordinate Gradient, Zou et al. réf [47], Algorithme 1, p.5) et **soft prompt obfuscation** (espace continu des embeddings, descente de gradient directe, Section 3.4, p.6). L'idée centrale est de trouver une "collision dans l'espace des prompts" : un soft prompt qui ne correspond à aucune représentation textuelle (hard prompt) exploitable, en exploitant la non-bijectivité du reverse mapping embedding→token (Section 2.3, p.3 ; Section 3.2, p.4). Objectif d'optimisation : minimiser la divergence des sorties (CE + KL) entre prompt original et obfusqué sur un jeu de prompts utilisateur représentatifs U (Eq. 4 et 5, p.5-6).
- **Donnees :** Modèle cible = **Llama 3.1 8B instruction-tuned**, chargé en quantization 4-bit, nucleus sampling top-p=0.95, température 0.7, 125 tokens/sortie (Section 5.1, p.7). Datasets : QA = TruthfulQA (817 questions, 800 retenues, split 640 train / 160 test), TriviaQA (~650 000 paires) ; Summarization = CNN/DailyMail (~312 000 articles), Samsum (~16 000 dialogues) (Section 4.1, p.6 ; Section 5.1, p.7). 7 styles testés (pirate, southern_usa, poem, stutter, david_attenborough, robot, friendly). 3 scénarios de placement Task/Style : Full, Style, Task (Section 4.2, p.6).
- **Resultat :** L'obfuscation **soft prompt** maintient l'utilité au niveau du prompt original (parfois supérieure) : sur CNN/DailyMail Full, BLEU passe de 13.79 (blank) à 46.57 (obf) vs 42.39 (original) ; Cosine 0.63→0.85 vs 0.83 (Table 4, p.9). Côté confidentialité, l'attaque de prompt injection (105 requêtes d'extraction par dataset, méthode de Zhang et al. réf [45]) donne **0.00 exact-match et 0.00 approx-match sur le prompt obfusqué pour les 7 styles**, contre p. ex. 15.50 exact / 27.25 approx pour le style 'pirate' sur le prompt conventionnel (Table 7, p.10). "none of the 105 attack queries were able to recover any part of the obfuscated system prompt across the datasets" (Section 6.1, p.10).
- **Limite :** Dans le scénario white-box le plus fort (Fluency Hard Prompt Optimization via GCG, attaquant connaissant le modèle ET l'embedding obfusqué), des fragments partiels redeviennent lisibles ("pirate accent", "southern accent"), Levenshtein 0.20 vs 0.12 random, Cosine 0.34 vs 0.27 (Table 10, p.12). Les auteurs reconnaissent : "replicating this attack scenario is very unrealistic, as it requires white-box knowledge of the model and the exact obfuscated soft prompt" (Section 6.3, p.12). Limite avouée additionnelle : la méthode requiert des **échantillons d'entrée** pour optimiser (Section 8, "Output dependency", p.13).

### Analyse critique

**Forces :**
- **Renversement conceptuel pertinent.** Au lieu de jouer au chat et à la souris ("reactive and ongoing cat-and-mouse game", Section 3, p.4) contre les attaques d'extraction, les auteurs acceptent la fuite et neutralisent sa valeur. C'est un changement de threat model défensif intéressant : on ne défend plus la *confidentialité du canal* mais l'*intelligibilité du secret*.
- **Évaluation multi-métriques honnête.** 8 métriques d'utilité (BLEU, ROUGE-L, METEOR, NIST_MT, characTER, ChrF, BERTScore, cosine — Section 4.3, p.6) + 4 métriques de similarité de prompt (Levenshtein, LCS, Jaccard, cosine). L'usage d'une baseline "blank" ET d'une référence "original" (même prompt, seed différente) encadre correctement les résultats (Table 1 note, p.8).
- **Trois attaques de déobfuscation gradées en connaissance adverse** (black-box prompt injection ; white-box token-space projection ; white-box fluency optimization) — démarche red-team défensive sérieuse (Section 6, p.10-12).
- **Comparaison à un baseline fort (LoRA finetuning).** L'obfuscation égale LoRA en utilité tout en étant ~328× plus compacte en stockage ("the finetuned adapters are approximately 328 times larger than the corresponding obfuscated soft prompt embeddings", Section 5.4, p.9-10).
- **Reproductibilité élevée :** code public (GitHub Dormant-Neurons/prompt_obfuscation) + artefacts Zenodo (DOI 10.5281/zenodo.15601914), datasets publics, hyperparamètres détaillés (Section "Open Science", p.13).

**Faiblesses :**
- **Un seul modèle et un seul ordre de grandeur** (Llama 3.1 8B, 4-bit). Aucune généralisation à GPT-4, Claude, Mistral, ni à des modèles >8B. L'argument "many systems utilize open-source models" (Section 6, Full-access, p.11) ne couvre pas les modèles fermés (où l'attaquant n'a justement pas l'accès embedding requis pour déployer un soft prompt — voir contrainte d'applicabilité ci-dessous).
- **System prompts très courts dans l'expérience principale** ("approximately ten tokens", Section 4.3, p.6). Le case study Manga Miko (Section 5.3, p.9) tempère ce point mais reste un cas unique. La robustesse sur des system prompts longs et structurés (chaînes d'outils, garde-fous médicaux multi-règles) n'est pas démontrée.
- **Contradiction interne reconnue pour le hard prompt.** Le hard prompt obfusqué fuite déjà partiellement de l'information ("related words can still be identified", Section 5.1, p.8) ; la régularisation de fluence (NLL) qui réduit la lisibilité dégrade simultanément l'utilité ("lower output similarity over all metrics for all scenarios", Section 5.1, p.8). Le hard prompt est donc largement abandonné au profit du soft prompt.
- **La métrique de fuite est un proxy.** Le succès d'extraction est mesuré via le dataset/critère de Zhang et al. [45] (exact-match = toutes les phrases sous-chaînes ; approx-match = ≥90% LCS des tokens). Un attaquant pourrait extraire de l'information *sémantique* sans match exact de tokens — ce que les métriques de similarité de prompt (Tables 8-10) tentent de capter mais sans juge sémantique fort.

**Questions ouvertes :**
- L'obfuscation tient-elle face à des attaques **adaptatives** (attaquant connaissant la méthode d'obfuscation et optimisant spécifiquement contre elle, p. ex. multi-turn crescendo) ? Non abordé par les auteurs.
- Le soft prompt obfusqué modifie-t-il la **surface d'alignement** (δ⁰) ? Un system prompt remplacé par un vecteur embedding hors-distribution pourrait dégrader ou modifier les refus de sécurité du modèle. Non testé par les auteurs (ils mesurent l'utilité de tâche, pas la robustesse safety).
- Transférabilité après mise à jour silencieuse du modèle (re-quantization, fine-tune) : un soft prompt est "inherently tied to the specific token embedding layer" (Section 6, p.10) — il casse si le fournisseur met à jour les poids. Non quantifié.

### Mecanisme (contribution cle)

**Idée centrale [ALGORITHME — méthode d'optimisation, sans garantie formelle de confidentialité].** Étant donné un system prompt original `s`, construire `s_obf` tel que (1) la fonctionnalité est préservée et (2) `s_obf` est inintelligible. La fonctionnalité n'étant pas mesurable directement, on définit un ensemble de prompts utilisateurs `U` et on minimise la divergence des sorties du modèle conditionné sur `s` vs `s_obf` (Section 3.2, p.4) :

> argmin_{s_obf} Σ_{u∈U} ℓ(s, s_obf, u)  (objectif d'obfuscation, Section 3.2, p.4, équation non numérotée)

**Hard prompt obfuscation (espace des tokens) :** initialisation aléatoire d'une séquence de 10 tokens, optimisation par GCG (Greedy Coordinate Gradient, réf [47]) car l'espace des tokens est discret. Loss = CE + KL (Eq. 4). Approche par fenêtre glissante de W tokens consécutifs (W=5) exploitant l'autorégressivité (Algorithme 1, p.5). Résultat : lisible mais fuite partielle ; régularisation NLL (L ← L − NLL(s_obf)) réduit la lisibilité mais dégrade l'utilité (Section 5.1, p.8).

**Soft prompt obfuscation (espace des embeddings) — la contribution forte :** on optimise directement le vecteur d'embedding `ŝ_obf = φ(s_obf) ∈ R^{t×d}` par descente de gradient (Adam, lr=0.01). Loss redéfinie sur le modèle privé de sa couche d'embedding `M_{θ\Emb}` (Eq. 5). La défense repose sur la **non-bijectivité du reverse mapping** embedding→token : "Vectors not explicitly present in the lookup table cannot be accurately converted to specific tokens" (Section 2.3, p.3). Plusieurs soft prompts distincts mappent vers un même hard prompt, donc projeter l'embedding obfusqué vers les tokens les plus proches (token-space projection, Section 6.2) ne récupère que des fragments aléatoires. Tag épistemique : [EMPIRIQUE] — la confidentialité est démontrée empiriquement contre 3 attaques, PAS prouvée formellement. Les auteurs le disent : "While this approach does not guarantee that the resulting prompt is devoid of meaningful information, our empirical evaluation suggests that obfuscated prompts occupy distinct regions in prompt space" (Section 3.2, p.4).

### Formules exactes

- **Eq. 2** (formalisation prompt) : `M_θ(x) = M_θ(s, u)` où `s` = system prompt, `u` = user input (Section 2.2, p.3). [DEFINITION]
- **Eq. 3** (soft prompt) : `x̂ = φ(x) ∈ R^{t×d}`, φ = table de lookup d'embedding du modèle, d = dimension embedding (Section 2.3, p.3). [DEFINITION]
- **Eq. 4** (loss hard prompt) : `ℓ(s, s_obf, u) = L_CE(M_θ(s,u), M_θ(s_obf,u)) + L_KL(M_θ(s,u), M_θ(s_obf,u))` — CE assure les bons tokens, KL régularise vers des distributions similaires (Section 3.3, p.5). [ALGORITHME]
- **Eq. 5** (loss soft prompt) : `ℓ(ŝ, ŝ_obf, u) = L_CE(M_{θ\Emb}(ŝ,u), M_{θ\Emb}(ŝ_obf,u)) + L_KL(M_{θ\Emb}(ŝ,u), M_{θ\Emb}(ŝ_obf,u))` (Section 3.4, p.6). [ALGORITHME]
- **Eq. 6** (attaque fluency déobfuscation) : `L ← L + NLL(proj(ŝ_obf))` — l'attaquant ajoute la Negative Log-Likelihood pour optimiser vers un prompt lisible (Section 6.3, p.11). [ALGORITHME — attaque]
- **Régularisation de fluence côté défense** : `L ← L − NLL(s_obf)` (soustraction → réduit la lisibilité) (Section 5.1, p.8).
- **Critères de succès d'extraction** : `exact(s,g) = 1[∀ phrase s de s : s sous-chaîne de g]` ; `approx(s,g) = 1[|LCS(tokens(s),tokens(g))| / |tokens(s)| ≥ 90%]` (Section 6.1, p.10-11). [METRIQUE — proxy de fuite]

Lien glossaire AEGIS : aucune formule existante F01-F72 directement équivalente ; candidat nouveau "métrique de fuite system prompt (exact/approx match)" et "objectif d'obfuscation par collision soft prompt".

### Pertinence these AEGIS

- **Couches delta :** C'est une **DEFENSE**, pas une attaque. Elle agit principalement sur **δ⁰** (couche système / system prompt) : elle ne renforce pas le contenu des instructions de sécurité mais en protège la *confidentialité* en les rendant inintelligibles après exfiltration. Effet secondaire potentiel non étudié sur la couche d'alignement RLHF (le remplacement texte→embedding hors-distribution pourrait modifier le comportement de refus — risque à investiguer côté AEGIS). Pertinent pour le sous-axe "protection contre prompt leaking" plutôt que pour le hardening du contenu lui-même.
- **Conjectures :** Nuance pour **C1/C2** (porosité δ⁰ / le system prompt fuit). Le papier *confirme empiriquement* la porosité (les prompts conventionnels fuitent : jusqu'à 15.50 exact-matches / 105 attaques, Table 7) — ce qui **soutient** la prémisse de C1/C2. Mais il propose une mitigation qui **affaiblit l'exploitabilité** de cette porosité : la fuite reste possible mais devient sans valeur (0/105 sur le soft prompt obfusqué). À traiter avec prudence : la défense ne ferme PAS le canal de fuite, elle dévalue son contenu — distinction importante pour ne pas surinterpréter comme une réfutation de C1. Neutre voire défavorable à toute conjecture AEGIS qui affirmerait "le system prompt extrait est toujours exploitable".
- **Defense AEGIS :** Candidat nouveau pour la taxonomie 87 techniques — catégorie "system prompt protection / IP protection" via obfuscation soft prompt (distinct des techniques de detection/sanitization existantes). Limite d'applicabilité forte à documenter : nécessite l'accès à la couche d'embedding du modèle déployé → inapplicable aux modèles fermés derrière API (Groq llama-3.3-70b en mode API standard n'expose pas l'injection d'embeddings system). Applicable surtout en self-hosting (Ollama local) où AEGIS contrôle la pile d'inférence.
- **MITRE ATLAS :** AML.T0051 (LLM Prompt Injection) — vecteur ciblé ; plus spécifiquement le sous-objectif d'**extraction / prompt stealing** (system prompt leaking). Référence directe à la méthode d'extraction de Zhang et al. [45].
- **OWASP LLM :** LLM07 (System Prompt Leakage — catégorie 2025) en cible principale ; LLM01 (Prompt Injection) comme vecteur d'extraction utilisé dans l'attaque black-box (Section 6.1).
